## Phase 2: the exhaustive state corpus

The ask: a set of datasheets that exercises **every state the product can be in**,
run end to end, with the results recorded as if a person had done it by hand.

### 2a. Name the state space first

A corpus is only "exhaustive" against a written-down list of states. From the code,
the axes are:

| Axis | Values |
| --- | --- |
| Input path | upload / part-number search |
| Document | clean text layer / scanned, no text layer / wrong document for the part / family with many packages / single package |
| Mounting | SMD / through-hole |
| Arrangement | `single` / `dual` / `quad` / `grid` |
| Thermal pad | absent / present / present with vias |
| Land source | datasheet's printed footprint / IPC-7351B computed / IPC-7251 holes |
| Package chooser | 0 options / exactly 1 / several |
| Outcome | ships unaided / ships after questions / refuses |
| Refusal | the five codes above |
| Confirmation | all confirmed / some flagged / over `MAX_FLAGGED` = 5 |
| Settings | density A/B/C, `footprintSource` both values, forming die blank vs supplied |
| Export | kicad / altium / cadence |

**The cell is the unit, not the datasheet.** One part covers several cells. The
deliverable is a table of cells with the part that covers each, and cells with no
part are the finding, because that is the state nobody has ever tested.

### 2b. Where the datasheets come from

- Reuse the 60 tuned parts first. They already cover many cells for free.
- Add only what fills an empty cell.
- **Never open the hold-out or blind corpora for this.** `holdout.ts` starts a
  measurement the moment it is imported.
- New parts go in a new `.states-cache/`, gitignored like every other corpus.

Estimate: 25 to 40 new datasheets. **~$1.25 to $2.00.**

### 2c. Running them "as if through the UI"

The honest reading of the ask is a real browser, not a route call, because the
2026-08-24 defect was a dead page while every route answered correctly.

`bench:browser` already drives a real Chrome through 29 stages. The work is to
generalise it from one datasheet to a corpus and to record per-part results
rather than pass/fail.

Output, one row per part, written to `STATES-2026-09-03.md` plus a JSON sibling:

    part, document class, intent, package chosen, what read cleanly,
    what was asked and why, what was flagged, what shipped, refusal code if any,
    seconds, model spend

- Done when: every cell is covered or is named as uncoverable, and the file exists.
- Risk: browser runs are slow. Reads are cached after the first pass, so a
  re-run is cheap; the first pass is the paid one.

## Phase 3: the suite UI on `main`

### What the branch actually is

`/suite` is **purely additive**: `src/app/suite/*` plus `src/lib/intent.ts` and
`src/lib/readprogress.ts`. It owns navigation and state only. The flow:

    first run (settings, then account; skippable)
      -> home: choose intent, then drop a PDF or name a part
      -> identify: deterministic, ~1s, NO model call
         (if the intent needs a footprint: choose the package BEFORE the read)
      -> the read: ~90s, one model call, aimed by the intent
      -> output

Intent is chosen **before** the read because the reader is field-directed, a
package belongs to a footprint and nothing else, and every pin reader takes the
package as an argument. That ordering is the load-bearing decision.

### The two things that will bite

**1. `bench:browser` is hardwired to `/` and to `page.tsx` selectors.** The moment
`/` becomes the suite, the only instrument that proves this app runs in a browser
goes blind, and it will still report green because its stages are keyed to
selectors that no longer exist. This is the 2026-08-24 failure shape exactly.

  **So the bench is extended to the new UI BEFORE `/` flips, not after.**

**2. The branch is on Next 16 and `main` is on Next 15.** The branch's own handoff
records that `npm run build` fails to bundle on 16. `main` builds clean today.
**Port the components, not the version bump.** If a suite component turns out to
need Next 16, that is a separate decision with its own evidence, not a rider on a
UI port.

### What the research says to change, and one of it contradicts the handoff

**Package choice before the read: engineers say no.** `HANDOFF.md` calls
choose-before-read "the load-bearing decision". Working designers, unprompted:

  *"As an electronic designer I choose a part, at the same time I choose the
  package... When I'm done I hand these to the PCB designer."*
  *"In every design I've worked on, the design engineer specifies the package."*

Gating on it asks the user to re-enter what the MPN already encodes. **But our
pipeline genuinely needs the package early** (every pin reader takes it as an
argument), so this is a real tension rather than a misunderstanding. The shape
that satisfies both, and which our own `packageOptions` and outline-code work
already assume:

- MPN given -> resolve the package FROM the MPN, read, then report which one and
  why, with a switch. Zero questions.
- Bare family datasheet -> read first, then present the packages the document
  offers AS A RESULT of the read.

Package identity is an output, not an input. **This one needs the cofounder's
agreement before it is built either way.**

**Never ask about IPC density level.** Most users do not know, and the ones who do
ask their contract manufacturer rather than us. A beginner asking which to use was
told *"I suggest you just forget about those density levels"*. Pick B, name the
standard, allow a change. Our current settings screen is already close to this.

**Show dimensions with the datasheet's own letters** (D, E, e, L, b) beside the
drawing region they came from, so an engineer verifies 1:1 by eye. Requested
almost verbatim: converting a drawing's dimensions into a tool's internal model
*"isn't hard, but it is cumbersome and error-prone"*.

**Show the delta between the printed footprint and the computed IPC one.** Which
to prefer is genuinely contested by experienced people on both sides. We hold both
readings, so the highest-value move is to show both and cite them rather than pick
silently. No competitor has this.

**What comes out is a review surface, not a ZIP.** Nobody trusts an
auto-generated footprint at any experience level, and they never will. The
correct posture is not to earn trust so they stop checking, it is to make checking
cheap. A customer wrote our spec in 2022 without knowing it:

  *"Things need to be documented to the point that I can trace where that
  footprint came from, why it has the dimensions it does, and what it's good
  for... it's the difference between 'Footprint Club' and 'Standard Library'."*

**One warning aimed straight at us.** The most damaging thing a tool in this space
can do, per a KiCad forum thread about SnapEDA, is publish a correctness standard
and then violate it: *"they don't even follow their own standard."* We publish a
correctness doctrine, so that risk is ours.

## Phase 4: LTspice, after four research passes

Four agents researched this. The answers changed the phase substantially, and two of
them contradict assumptions in `HANDOFF.md` and `SPICE.md`.

### Q1, generate or find: FIND AND VERIFY. Do not build a model generator.

The mechanism is structural, not a tooling gap:

- Vendor models come from measured silicon and process extraction. From EDAboard:
  *"For the very simplest components (individual transistors, diodes), it is
  possible to create models from datasheets. However, for anything more
  complicated than a transistor, such as an IC, it takes much more than a
  datasheet."*
- **Every tool that has ever generated SPICE from a datasheet covers discretes
  only**: Qorvo QSPICE, Altium's SPICE Model Wizard, PSpice Model Editor,
  Intusoft SPICEMOD. Four decades, serious vendors, no IC macromodel generator.
- **No published tool generates an op-amp macromodel from a datasheet.** That is
  either an opportunity or a warning, and three other findings say warning.
- Open-loop output impedance is *"usually not stated in the datasheet at all"*,
  and it is what stability analysis needs. Stability is the principal engineer's
  main reason to simulate at all.
- The best prior art, SPICEMOD, fills missing values *"by estimation"*. Our
  rules forbid exactly that.

**The argument that settles it under our own rules: a generated model's
PARAMETERS have sources, but its TOPOLOGY does not.** We would ship a structural
assumption we cannot cite. That is rule 1, directly.

### The step that is actually ours

From the KiCad 8 simulation docs: **"Pin mapping is the most common source of
simulation problems with external models."**

Binding a `.subckt`'s node order to the right symbol pins is the thing we already
hold the data for and that SnapEDA, Ultra Librarian and SamacSys all treat as an
afterthought. That is the feature, not model generation.

### Q4, the second means: the artefact is EXECUTABLE, and that solves it

This is the best answer available and CAD never had it. A fetched or emitted model
can be **run**, and its measured behaviour compared against the datasheet numbers
we already extract:

    the datasheet's stated GBW, Aol, slew rate, Vos, output swing
      against
    the same quantities MEASURED by simulating the model

Those are readings by genuinely different means: one is text off a page, the other
is a simulator solving a circuit. They share no failure mode. It is also exactly
what TI tells its own users to do, in a post titled *"SPICE op amp macromodels:
trust but verify"*, in which TI documents its own LMV844 model failing to match
its own datasheet.

**The validation suite already exists and is public**: TI AN-1516, *SPICE
Universal Test Circuits* (SNOA475F), twelve tests, each shown beside the datasheet
figure it reproduces.

### Q3, min/typ/max: a SETTING, and not named min/typ/max

There is no single right answer, and the naive framing is a trap. Measured across
two real TI datasheets read in full:

- Aol: worst case is the **MIN** column.
- Vos, Ib, IQ, output headroom: worst case is the **MAX** column.
- **CMRR: worst case is MIN when printed in dB (OPA2991) and MAX when printed in
  uV/V (LM358B). Same parameter, same vendor, opposite column.** A "use the max
  column" rule ships 316 uV/V of CMRR error labelled as excellent rejection.
- **GBW, slew rate, phase margin, Zo, noise and input impedance are TYP-ONLY.**

So a "worst-case" datasheet-derived model is not a worst-case model; it is a mixed
model. The setting is `typical` / `worst-case`, and **every parameter is labelled
with which column it came from**. Silent typical substitution is refused.

### Q2, device class, if we ever generate: op-amps, and only op-amps

Most-used analogue part, the only class with a 50-year closed-form datasheet-to-
model mapping (Boyle 1974), five terminals and a near-identical spec table across
vendors. Required set is **Aol, GBW, slew rate, output swing, supply rails, and
phase margin**. Phase margin is required, not a refinement: a single-pole model is
unconditionally stable and will show a clean step response for a circuit that
rings on the bench. That is the model being confidently wrong rather than merely
incomplete.

Not attempted from a datasheet: LDOs, switching controllers, logic (IBIS), data
converters. Discretes are a different problem (curve fitting, not table reading)
and a separate track if ever.

### Q8, the file set and pin order: answered, and our worry was misplaced

`.sub` for the model, `.asy` for the symbol. `.asc` is a schematic; `HANDOFF.md`
has this backwards and `SPICE.md` already corrects it.

`SpiceOrder N` is purely positional against the `.subckt` terminal list, and
**there is no way to express a package pin in a `.asy` at all**. LTspice's own
stock symbols disagree with each other about which input is pin 1: `opamp.asy`
says inverting, `opamp2.asy` says non-inverting, and neither matches a DIP-8.

So a KiCad symbol numbered by package pin and an LTspice symbol ordered by
`SpiceOrder` are SUPPOSED to differ. The real invariant:

    ONE internal ordered terminal list feeds BOTH the .asy SpiceOrder and
    KiCad's Sim pin-assignment field. Never derive them separately.

Use `.lib` rather than `.include` for model files: `.lib` ignores stray
global-scope elements that would otherwise inject components into the user's
schematic.

### Q5, Q6, Q7: settled from our own code

- **Q5, is a parameter block one flag or many?** One. `confirm.ts` has seven ids
  for the entire CAD output and `pinout` is one item whether the part has 8 pins
  or 144. A parameter block off one specification table is one glance. The
  `MAX_FLAGGED` budget survives, by existing precedent rather than special case.
- **Q6, `/api/model` or a fourth format?** A fourth `exportFormat`.
  `resolveForExport` runs at route line 107, before `createExportZip` at 256, so a
  fourth format inherits the traceability gate for free. A new route would
  re-implement the gate and the four refusal codes, which is the two-implementations
  hazard. Note line 86 hardcodes the three format names instead of deriving from
  `exportFormats`; fix that when adding one.
- **Q7, the `both` bundle?** One zip. `createExportZip(part, format, options)`
  already has the shape.

### The bench, proven able to go red before it is built

An agent built a model with In+/In- swapped in the `.subckt` header. Re-run and
confirmed directly on this machine with ngspice 47:

    stage                          correct    swapped
    static lint (arity, order)     pass       PASS      <- blind to it
    DC operating point + gain      pass       PASS      <- g = 2.000040
    closed-loop transient          pass       FAIL      <- rc = 1

**A linear op-amp with positive feedback has a perfectly valid DC solution at
exactly the right gain.** Only the transient catches inverted inputs. So the gate
is three stages and the transient is mandatory.

Two traps: ngspice returns **exit 0 on a singular matrix**, so assert inside a
`.control` block rather than trusting exit codes; and in `-b` mode a valid netlist
with no `.print` and no `.control` block exits 1.

### The measurement that must come first, and it is FREE

**Nobody publishes vendor SPICE model coverage.** Two agents looked and neither
found a figure. It decides the size of this whole feature, and we can measure it
directly against our own corpus with no model spend:

For the 60 tuned parts, count how many have a vendor SPICE model that is
(a) findable, (b) plaintext rather than encrypted, (c) actually runnable.

That last one matters more than it looks: **ngspice cannot run LTspice models
that use `A` devices** (OTA, SCHMITT), and LTspice's own shipped
`UniversalOpamps2.sub` fails under ngspice for exactly that reason. So the free
verifier works on models we emit and on plain-SPICE vendor models, but not on all
of them. Verifying the rest needs real LTspice under wine on Linux.

**If coverage is low, find-and-verify is small and the answer may be neither.**
Measure before committing.

### The finding that questions the whole phase

From the top-voted Stack Exchange answer on how real boards get simulated:

  *"The widespread use of simulation of entire boards is mostly a myth... Generally
  you simulate the bits you are not sure about, which is usually less than 10% of a
  design (the rest is 'data sheet engineering')."*

Simulation happens during architecture, on a few parts, often before the part is
chosen. Library creation happens during schematic capture, on every part.
**Different moment, different person.** The research verdict was that a SPICE
feature would dilute the honesty pitch for a job the user is not doing that day.

That is a product call, not an engineering one, and it belongs to you and your
cofounder. The plan above is what to build IF the answer is to build it.

## A gap in our doctrine the research found

Our invariant catches a datasheet that contradicts itself. It does **not** catch a
datasheet that is consistently wrong, and physical-dimension errors are common
enough that engineers have a heuristic for them:

  *"For many years now I have observed that component data sheets are often in
  error when it comes to physical dimensions... If a physical dimension does not
  seem to be an even number in either the English or the metric system, perhaps it
  should be double checked."*

`PACKAGE_ORACLE` and the pin-name oracle are hand-read from the same documents, so
they cannot catch this class either. Not in scope for these four phases, but it is
the next real hole and it should be written down before it is forgotten.
